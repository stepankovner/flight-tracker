# Решения и отклонения от ТЗ

Документ ведётся по правилу из `CLAUDE.md`: всё, что в SPEC.md помечено «перепроверить», сверено с документацией; все пробелы в логике закрыты решениями ниже.

## 1. Сверка внешних API (28.09.2026)

### Travelpayouts Data API
Источник — [Aviasales Data API](https://support.travelpayouts.com/hc/en-us/articles/203956163) (обновлена 06.09.2026) и [API rate limits](https://support.travelpayouts.com/hc/en-us/articles/4402565416594).

| Что в ТЗ | Что в документации | Как сделано |
|---|---|---|
| `prices_for_dates`: параметры `origin, destination, departure_at, return_at, one_way, direct, sorting, unique, limit, page, currency, market` | Совпадает. `limit` по умолчанию 30, максимум 1000 | Используются все параметры. `limit` = 200, см. §2 |
| Токен в заголовке `X-Access-Token` | Можно в заголовке или в `token=` | Только заголовок, в URL токена нет |
| В ответе, возможно, есть `found_at`/`expires_at` | В `prices_for_dates` этих полей **нет** (есть у старых v1/v2 методов) | Схема их принимает, если появятся. Возраст цены берём из `search_date=DDMMYYYY` внутри `link` (точность до дня): «найдена сегодня / вчера / N дней назад» |
| — | `one_way=true` группирует по дате: один (самый дешёвый) билет на дату | Для «в одну сторону» получаем самый дешёвый билет на каждый день. Если его отсекает фильтр (время, авиакомпания), второй по цене вариант того же дня не виден. Это ограничение источника |
| — | При ошибке `"data": {}` и `success:false` | Обрабатывается как ошибка клиента, а не «смена схемы» |
| Бутстрап: `grouped_prices` и/или `month-matrix` | `grouped_prices` (v3) поддерживает `group_by=departure_at` и `min/max_trip_duration` | Только `grouped_prices`; `month-matrix` (v2) не нужен |
| Лимиты API | 600 запросов/мин для v3-методов, 429 с `X-Rate-Limit-Reset` | Backoff учитывает заголовок |
| Autocomplete `places2` | Работает без токена, есть `weight` | Проверено живым запросом. `weight` используется для однозначного выбора |
| Формат поисковой ссылки `/search/{ORIG}{DDMM}{DEST}{DDMM}{adults}` | Подтверждён примерами `link` (`/search/MAD2807BCN26081`) | Для нескольких взрослых меняем последнюю цифру |

### Проверка на живом API (28.09.2026, `npm run smoke` и замеры)
- Схема совпала; появилось недокументированное поле `gate` (агентство), `found_at`/`expires_at` нет.
- **API отдаёт меньше `limit` даже на неполных страницах:** при `limit=200` пришло 192 записи, на второй странице ещё 184. Поэтому последней считается страница, где записей < 75% от `limit`, а не просто < `limit`.
- MOW→IST, ноябрь 2026, месяц×месяц туда-обратно: 434 записи, 318 КБ при `limit=1000`. В одну сторону: 30 записей (одна на дату), 20 КБ.
- `one_way` при заданном `return_at` ни на что не влияет: выдача та же.
- Разбор + zod + фильтры + кэш на реальном ответе: ~0,45 мс на 100 КБ на Apple Silicon. На Workers закладываем в 2–3 раза больше, отсюда бюджет 800 КБ на тик (§2).

Источник — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) (05.09.2026), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

| Лимит | Значение | Совпадает с ТЗ? |
|---|---|---|
| Запросов в сутки | 100 000 | да |
| CPU на вызов (HTTP и Cron) | 10 мс | да |
| Subrequests на вызов | 50 | да, **но** см. ниже |
| Запросы D1 на вызов (Free) | страница D1: **50**; страница Workers: «internal services 1000» | противоречие в документации — проектируем под строгий вариант |
| Одновременных соединений | 6 | учтено (параллельность 6) |
| Cron-триггеров на аккаунт | 5 | используем 2 |

| D1: размер БД | 500 МБ | с запасом |

## 2. Последствия лимитов (отклонения от ТЗ)

1. **D1-вызовы считаются в бюджет subrequests.** Класс `Budget` считает и `fetch`, и обращения к D1. Всё чтение и запись тика собраны в несколько `db.batch()`: около 6 вызовов D1 на тик.
2. **Запросов к API за тик — 24, а не 30.** 24 — максимум одного watch, то есть любой допустимый watch помещается в тик. Бюджет тика: 24 API + до 8 сообщений Telegram + около 8 вызовов D1 < 50. Тест проверяет это на 20 watch.
3. **`limit=200` вместо максимума 1000.** Выдача отсортирована по цене, поэтому следующая страница догружается, только если последняя цена на странице ≤ целевого порога или ни один оффер ещё не прошёл фильтры (например, ночи). Максимум 3 страницы.
4. **CPU-бюджет тика — по замерам на самом Workers.** Временный Worker-бенчмарк на реальном ответе API (143 КБ, 191 запись):
   - холодный код — около 10 мс CPU на первом прогоне;
   - дальше ~2,5 мс на страницу, из них `JSON.parse` 0,8 мс и **zod 1,8 мс** (≈ 9 мкс на запись).

   Что сделано:
   - Записи на горячем пути разбираются вручную (`fastParseItem`); zod остаётся для конверта ответа и `npm run smoke`, паритет со схемой проверяет тест. Разбор стал 0,7 мс на страницу.
   - Объём ответов оценивается заранее по типу запроса: месяц×месяц ≈ 150 КБ, конкретные даты ≈ 50 КБ, в одну сторону ≈ 25 КБ. В тик набираются watch, пока оценка ≤ 450 КБ (≈ 3 помесячные страницы). Первый берётся всегда, чтобы широкий watch не откладывался бесконечно; остальные уходят в следующий тик (round-robin). Порог по фактическим байтам ограничивает только догрузку 2-й и 3-й страниц.
   - **Cron `*/5` вместо `*/15`**: те же проверки идут меньшими порциями. Пропускная способность выше, пиковый CPU одного вызова ниже.
   - **Вес одного watch** ≤ 900 КБ по оценке (≈ 6 помесячных пар туда-обратно), иначе мастер откажет с подсказкой, как сузить. Лимит 24 запроса из ТЗ сохраняется.
   - **Итог на боевом Worker (28.09.2026, `wrangler tail`):** пустой тик 2–10 мс CPU, проверка watch с запросом к API 16 мс (из них ~10 мс холодного старта), все вызовы `ok`. Число оборванных тиков видно в heartbeat и `/status`.
   - **Самовосстановление.** После отбора watch тик пишет маркер `tick_inflight`. Если следующий тик находит маркер (прошлый оборвался, например, по CPU), он отодвигает те watch в конец очереди с ошибкой, вдвое урезает объём (до 25%, затем восстанавливает ×1,25 за удачный тик) и пишет админу. Один «ядовитый» watch не блокирует остальных, а после 10 таких ошибок подряд пользователь получит сообщение.
5. **В `observations` пишем 10 самых дешёвых подходящих офферов за проверку, а не все.** При 20 watch × 24 проверки × «все офферы» лимит 100k записей в сутки кончается. Для авто-режима достаточно `daily_min`, для истории — топа.
6. **Второй индекс `observations(watch_id, depart_date, return_date)` не создан.** Ни один запрос его не использует, а каждая вставка давала бы ещё одну запись.
7. **`zod/mini` вместо `zod`.** Полный zod v4 занимал 762 КБ из 1,1 МБ бандла, Cloudflare прямо советует экономить на нём память. После замены бандл 430 КБ (98 КБ gzip).
8. **Тяжёлая работа из вебхука (первая проверка, `/check`) идёт в `ctx.waitUntil`** с дедлайном 20 с. Telegram сразу получает 200 и не повторяет апдейт.

## 4. Закрытые пробелы логики

- **Год в датах.** Для конца окна подставляется ближайший будущий год, начало ставится не позже конца (переход через Новый год). Прошедшее начало сдвигается на сегодня, и об этом пишется. Конец дальше года вперёд обрезается: у Aviasales там нет данных.
- **Дополнительные форматы дат:** `15-30.11`, `15-30 ноября`, `15 ноября - 2 декабря`, `в ноябре`, `20.11 ±3`, ISO `2026-11-15`.
- **«Без ночных вылетов»** — вылет с 06:00 до 23:00 по местному времени аэропорта вылета.
- **Пересадки** проверяются в обе стороны. **Длительность** — у каждого направления.
- **Даты и время** оффера берутся локальные, из строки с offset, без пересчёта в UTC.
- **`daily_min`** считается по суткам UTC. Сегодняшний день в медиану не входит: сегодняшние цены с ней как раз сравниваются.
- **Бутстрап:** `grouped_prices` за месяцы окна ±1, до 6 запросов. Baseline — медиана минимумов по датам вылета, нужно ≥ 3 точек. Если данных нет, повтор через 24 ч. После 5 дней собственной истории бутстрап не используется.
- **Повторные уведомления.** Отправленные офферы, в том числе из «ещё N», сразу записываются в `notified`, иначе следующий тик прислал бы их снова. Если текущая цена уже ниже порога в «точке отсчёта», она тоже помечается и не дублируется тиком.
- **Дайджест** считается одним сообщением дневного лимита. Предупреждение о лимите — раз в сутки. Отложенные уведомления старше 36 ч выбрасываются: цены из кэша устаревают.
- **Срочные** (ниже `max_price` на ≥ 30%) обходят тихие часы и приходят без звука, но не обходят дневной лимит.
- **Ответы на действия пользователя** (`/check`, точка отсчёта) не ограничены лимитом. Системные сообщения в тихие часы идут без звука.
- **Правка watch.** Смена маршрута, типа, дат или ночей сбрасывает историю: старая медиана несопоставима. Смена цены или фильтров историю сохраняет. Истёкший watch с новыми датами снова становится активным.
- **Доступ.** Любое сообщение разрешённого пользователя привязывает его, не только `/start`. Группы и каналы игнорируются.
- **Путь вебхука** — `/tg/` + 32 hex от SHA-256 секрета. Отдельная переменная не нужна, секрет в URL не светится.
- **Username в секретах Worker**, а не в `wrangler.toml`: репозиторий публичный.
- **Ошибки API.** 401 → сообщение админу раз в 6 ч и остановка тика. 429 → пауза 2 → 4 → 8 → … → 120 мин (не меньше `X-Rate-Limit-Reset`), после 4-го подряд — сообщение админу. 5xx/таймаут → один повтор. Ошибки 401/429 не увеличивают `error_count` конкретного watch.
- **`/status`** (только админ) добавлен вне ТЗ: счётчики, пауза API, время последнего тика.
- **Валюта.** Берётся из `DEFAULT_CURRENCY` (rub). Порог «−300 ₽» для других валют задан таблицей в `config.ts`.

## 5. Процесс и окружение

- **Node 22+, а не 20:** Node 20 снят с поддержки в апреле 2026, а `node:sqlite` (тесты и Docker) нужен ≥ 22.13.
- **Зависимости сверх §3:** `tsx` (запуск TS-скриптов на любом Node 22), `@vitest/coverage-v8` (требование покрытия ≥ 85%), `@types/node`. `msw` не понадобился: хватило ручных фейков.
- **Интеграционные тесты** идут на настоящем SQLite (`node:sqlite`) с теми же миграциями и тем же `Repo`, что в Worker.
- **Коммиты по этапам** сгруппированы по слоям (ядро → провайдер → БД → задачи → бот → документация), чтобы каждый коммит собирался и проходил тесты.
- **Название.** По просьбе владельца продукт называется **FlightTracker**. В приветствии берётся имя бота из BotFather. Имена ресурсов Cloudflare (Worker и D1 `farewatch`) оставлены как есть: переименование Worker меняет URL вебхука, а D1 переименовать нельзя без переноса данных.
- **Маршрут одной строкой.** На шаге «Откуда» можно ввести весь маршрут: «Москва - Алматы», «из Москвы в Алматы». «Голый» дефис сначала проверяется как одно название («Улан-Удэ»).
- **Порядок деплоя** отличается от §13: сначала `wrangler deploy`, потом секреты, потому что `wrangler secret bulk` требует уже существующий Worker.
